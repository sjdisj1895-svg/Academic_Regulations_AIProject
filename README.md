# AI 기반 대학·산학협력단 규정집 통합 검색 시스템

경상국립대학교의 **대학 규정**(학칙/규정/지침)과 **산학협력단 규정**을 한 곳에서
조·항 단위로 검색하고, 담당부서까지 원스톱으로 확인할 수 있는 AI 검색 시스템입니다.

- 기획 문서: [`PRD.md`](PRD.md) (목적·요구사항·MVP)
- 작업 계획: [`TASKS.md`](TASKS.md) (T1~T5 단계별 계획)
- 구현 프롬프트: [`PROMPTS.md`](PROMPTS.md)
- 파이프라인 실행 방법: [`scripts/README.md`](scripts/README.md)

> ⛔ **T11 롤백**: 질문형 자연어 질의 정확도를 높이려고 임베딩 모델을 BGE-M3로 교체했으나, 실측 결과 완전히 무관한 질문("주식 시세 알려줘" 등)도 유사도가 0.6~0.93으로 비정상적으로 높게 나와 관련 질의(0.88~0.99)와 구간이 겹쳐버렸습니다. T9에서 어렵게 만든 "무관한 질문은 거절" 안전장치가 무력화되는 심각한 부작용이라 즉시 KR-SBERT로 원복했습니다.
> 🎉 **T12 완료**: 대신 ① 1차 검색 결과 상위 후보만 cross-encoder로 다시 정밀 비교하는 **재순위화(reranking)** 를 AI 질문하기(RAG) 경로에 추가하고, ② 조문마다 소속된 **장(章) 제목**을 함께 임베딩해 문맥을 보강했습니다. 부작용 없이 질문형 질의 정확도가 개선되었고, 즉시 응답이 중요한 일반 검색은 그대로 0.04초로 유지됩니다.

## 기술 스택 (Tech Stack)

> 원칙: **전부 무료(오픈소스)**, 별도 서버 구매 없이 **로컬 PC에서 실행 가능**,
> 학내 전산 환경(Windows)에서 운영 가능한 것을 기준으로 선정했습니다.

### 전체 구조 한눈에 보기

```
[T1 수집]            [T2 청킹·임베딩]              [T3 검색 API]         [T4 웹 화면]
대학 규정 사이트  ─┐
                   ├→ 텍스트 정리 → 조·항 청킹 → KR-SBERT 임베딩 → ChromaDB
산학협력단 게시판 ─┘   (Python)      (정규식)     (한국어 AI 모델)   (벡터DB)
                                                                      │
                              사용자 ← 웹 브라우저(HTML/JS) ← FastAPI 검색 서버
                                        (T4 예정)              (T3 예정, 하이브리드 검색)
```

### 2. T1 — 데이터 수집 (완료, 사용 중)

| 기술 | 역할 | 선택 이유 |
|---|---|---|
| **Python 표준 라이브러리** (`urllib.request`, `re`, `json`, `zipfile`) | 웹 페이지 요청, HTML 파싱, 데이터 저장 | **외부 라이브러리 설치가 전혀 필요 없어** 어느 PC에서든 즉시 실행 가능. 수집 대상 페이지 구조가 단순해 BeautifulSoup 같은 추가 도구 불필요 |

### 3. T2 — 청킹·임베딩·벡터DB (완료, 사용 중)

| 기술 | 버전 | 역할 | 선택 이유 |
|---|---|---|---|
| **정규식 기반 조문 청킹** (자체 개발, `chunk_rules.py`) | - | 규정을 '제0조 → 제0항(①②③)' 단위로 분할 | 한국 법령 조문은 형식이 일정해(제0조(제목), ①②③ 항) 정규식으로 정확히 분할 가능. 부칙·별표·별지도 별도 구획으로 보존 |
| **sentence-transformers** | 6.0.1 | 임베딩(문장→벡터 변환) 실행 프레임워크 | Hugging Face 표준 임베딩 프레임워크. 무료, 로컬 CPU에서 실행 가능 |
| **KR-SBERT** (`snunlp/KR-SBERT-V40K-klueNLI-augSTS`) | - | **한국어 특화 임베딩 모델** | 서울대 NLP 연구실 공개 모델. 한국어 문장 의미 유사도(STS)에 특화되어 규정 조문 검색에 적합. 무료이며 최초 1회 다운로드 후 **오프라인 실행 가능** (외부로 데이터가 나가지 않아 보안에도 유리) |
| **ChromaDB** | 1.5.9 | 벡터DB (임베딩 저장·유사도 검색) | 오픈소스 무료. **별도 DB 서버 설치 없이** 폴더(`C:\gnu_vectordb`)에 파일로 저장되는 임베디드 방식. 코사인 유사도 검색과 메타데이터 필터(출처/카테고리) 기본 지원 → 소규모 대학 규정(1만 청크 미만)에 충분 |

> ⚠️ 운영 참고: ChromaDB는 **한글이 포함된 폴더 경로**에서 인덱스 로딩 오류가 발생하여
> 영문 경로 `C:\gnu_vectordb`에 저장합니다. (환경변수 `GNU_VECTORDB`로 변경 가능)

## T6 — RAG 파이프라인 기반 구축 (검색 + LLM 연결 엔진)

질문을 넣으면 ①T2/T3의 하이브리드 검색으로 관련 조항을 찾고, ②그 조항만 근거로 삼아 AI가
답변 문장을 만들어내는 핵심 엔진(`scripts/rag_engine.py`)을 구현했습니다. 아직 웹 API·화면은
연결하지 않았고(T7~T8에서 진행 예정), 터미널에서 `python scripts/rag_engine.py`로 테스트할
수 있는 단계입니다. 기존 `scripts/search_engine.py`, `scripts/api_server.py`, `web/` 폴더는
전혀 변경하지 않았습니다.

### 구조 (3단계 파이프라인)

1. **검색(Retrieval)** — `retrieve()`가 `search_engine.py`의 `SearchEngine.search()`를 그대로
   호출해 관련 조항 상위 N개(기본 5개)를 가져옵니다. 관련성 최소 기준(T3에서 정한
   `MIN_VEC_SIM`/`MIN_BM25_SCORE`)을 이미 통과한 결과만 사용하므로 로직을 중복 구현하지 않았습니다.
2. **컨텍스트 조립(Context Building)** — `build_context()`가 조항들을
   `"[규정명] 제0조(제목): 본문..."` 형식으로 정리해 LLM에게 줄 참고자료 텍스트를 만듭니다.
3. **답변 생성(Generation)** — `answer()`가 참고자료와 질문을 프롬프트에 담아 LLM에게 전달하고,
   생성된 답변 끝에 근거 조항 목록(규정명+조항)을 항상 덧붙여 반환합니다.

### 사용한 LLM과 선택 이유

| 구분 | 내용 |
|---|---|
| 기본(로컬) 모델 | **Qwen/Qwen2.5-1.5B-Instruct** (허깅페이스 transformers) |
| 선택 과정 | 처음에는 더 가벼운 **Qwen2.5-0.5B-Instruct**로 검증했으나, 실측 결과 "참고자료에 없는 내용은 답하지 말라"는 지시를 제대로 따르지 못하고 구체적 금액("1년간 10억원 이상" 등)을 지어내는 **환각이 확인**되어 폐기했습니다. **Qwen2.5-1.5B-Instruct**로 교체 후 동일 프롬프트에서 참고자료에 없는 내용은 정확히 거부하고, 있는 내용은 정확히 인용해 답하는 것을 실측으로 확인해 최종 채택했습니다. |
| 선택 이유 | ①한국어를 포함한 다국어 instruct 모델로 별도 인증(gated) 없이 누구나 무료 다운로드 가능 ②Apache 2.0 라이선스 ③CPU(GPU 없는 학내 PC)에서도 로딩 20~45초, 200토큰 생성 약 8초로 실용적 ④환경변수 `GNU_RAG_LOCAL_MODEL`로 다른 모델로 손쉽게 교체 가능 |
| 외부 API(옵션) | 환경변수 `GNU_RAG_API_KEY`가 설정되면 OpenAI 호환 API(`GNU_RAG_API_BASE`, `GNU_RAG_API_MODEL`로 커스터마이즈)를 대신 사용. 현재 프로젝트에는 API 키가 없어 로컬 모델이 기본 동작 |
| 안전 장치 | 로컬/외부 어느 쪽도 사용할 수 없으면(모델 다운로드 실패 등) 에러를 내지 않고 `"[생성 불가: 검색 결과만 반환합니다]"` + 검색 결과로 안전하게 대체 |

### 환각 방지 설계

- 검색 결과가 0건(관련 조항 없음)이면 **LLM을 아예 호출하지 않고** 즉시
  `"해당 내용은 규정에서 찾을 수 없습니다."`로 응답 (불필요한 LLM 호출 방지 + 환각 예방)
- 로컬 소형 모델(1.5B)은 여러 차례 실측 비교를 거쳐, "참고자료 → 질문 → 답변 규칙" 순서로
  하나의 user 메시지에 담고 "답이 있으면 먼저 명확히 답하라"를 규칙 앞에 배치하는 프롬프트
  구조를 채택했습니다 (system 역할 지시나 거부 문구를 앞세우는 구조는 과잉 거부/앵커링 문제가
  실측 확인됨).
- 모델이 근거 출처 표시를 빠뜨려도, `answer()`가 검색 결과 기반 출처 목록을 답변 끝에 항상
  보강해 표시합니다.

### 검증 결과 (`python scripts/rag_engine.py` 실행)

| 테스트 질문 | 검색 결과 | 기대 동작 | 실제 결과 |
|---|---|---|---|
| "연구비 지원 한도가 얼마야?" | 5건(관련 조항은 있으나 구체적 한도 금액은 없음) | 지어내지 않고 거부 | ✅ "해당 내용은 규정에서 찾을 수 없습니다" + 근거 조항 표시 |
| "연구비 감사 관련 행정사무는 어느 부서가 지원해?" | 5건(정답이 top-1에 명확히 존재) | 정확히 답변 | ✅ "…산학협력단의 산학감사실이 지원…" + `[경상국립대학교 산학협력단 감사 지침] 제16조` 인용 |
| "오늘 서울 날씨가 어때?" (규정과 무관) | 2건(관련성 낮음) | 지어내지 않고 거부 | ✅ 날씨 정보 제공 불가를 명시하며 규정 무관 응답 |

세 케이스 모두 참고자료 밖 내용을 지어내지 않았고, 답변 끝에 근거 규정명·조항번호가 항상
표시됨을 확인했습니다.

## T7 — RAG 답변 생성 API 개발 (`/api/ask`)

T6에서 만든 `scripts/rag_engine.py`(검색→컨텍스트 조립→LLM 답변 생성)를 `scripts/api_server.py`에
연결해, 웹에서 호출 가능한 `POST /api/ask` 엔드포인트를 추가했습니다. 기존 `/api/search`,
`/api/chunks`, `/api/regulations`, `/api/filters`는 **전혀 변경하지 않았고**, `/api/ask`는
완전히 새로 추가된 엔드포인트입니다. 아직 웹 화면(UI) 연결은 하지 않았고(T8에서 진행 예정),
API 자체는 Swagger UI(`/docs`)나 `curl`/Postman 등으로 바로 테스트할 수 있는 단계입니다.

### 주요 구현 내용

- **입력**: 질문(`question`), 선택적으로 근거 조항 개수(`top_k`)·출처/카테고리 필터
  (`/api/search`와 동일한 방식 재사용)
- **출력**: AI 답변 문장(`answer`), 근거 조항 목록(`results` — `/api/search`와 완전히 동일한
  형식: 규정 구분·규정명·조항·본문 발췌·담당부서·원본 URL), 응답 소요 시간(`took_ms`),
  관련 여부(`found`), LLM 사용 여부(`used_llm`)
- **환각 방지**: 관련 조항이 0건이면 LLM을 호출하지 않고 즉시 "찾을 수 없음" + 추천 검색어
  (`suggestions`)를 반환 (T6 `rag_engine.py`의 설계를 그대로 재사용)
- **타임아웃 대비**: LLM 답변 생성을 별도 스레드에서 실행하고, `GNU_RAG_ASK_TIMEOUT`(기본

## T8 — RAG 챗봇 웹 화면(UI) 개발

T7에서 만든 `POST /api/ask`를 호출하는 화면을 기존 검색 화면(`web/index.html`, `style.css`,
`app.js`)에 자연스럽게 추가했습니다. 별도 페이지가 아니라 **기존 검색창 영역 위에 "검색" /
"AI에게 질문하기" 탭**을 추가해 전환하는 방식으로, 기존 검색 화면의 마크업·기능은 전혀
건드리지 않고 새 요소만 덧붙였습니다.

### 주요 구현 내용

- **모드 전환 탭**: 검색창 위에 `🔍 검색` / `💬 AI에게 질문하기` 탭 버튼 추가. 출처/카테고리
  필터는 두 모드가 공통으로 사용 (필터 변경 시 검색 모드에서만 즉시 재검색되도록 처리)
- **AI에게 질문하기 모드**: 질문을 입력하면 채팅 메시지(사용자 질문 말풍선 → AI 답변
  말풍선)로 표시되고, 답변 바로 아래에 근거 조항을 **기존 검색 결과 카드와 동일한 컴포넌트
  (`resultCardHtml`)** 로 재사용해 나란히 표시
- **AI 생성 답변 안내 문구**: 모든 AI 답변 말풍선 하단에 "⚠️ AI가 규정을 바탕으로 생성한
  답변이며, 법적 효력은 원본 규정을 따릅니다." 문구를 항상 표시
- **로딩/실패 처리**: 답변 생성 중에는 스피너 + "AI가 규정을 검색하고 답변을 작성하고
  있습니다..." 말풍선을 보여주고, 응답이 오면 그 말풍선을 결과로 교체. 관련 조항을 찾지
  못하면("찾을 수 없음") 추천 검색어 칩과 "일반 검색으로 전환" 버튼을 보여줘 검색 모드로
  즉시 넘어갈 수 있게 함. 요청 자체가 실패해도 같은 방식으로 안내 + 전환 버튼 표시
- **디자인 일관성**: 새로 추가한 요소(탭, 말풍선, 안내 문구 등)는 모두 T5.5의 GNU 브랜드
  색상 변수(`--color-signature`, `--color-primary` 등)를 그대로 사용
- **반응형**: 기존 반응형 미디어쿼리에 탭·채팅 말풍선 규칙을 추가해 모바일(375px)에서도
  자연스럽게 표시

## T9 — RAG 품질 검증 및 환각(hallucination) 방지 튜닝

T6~T8에서 만든 RAG 파이프라인 전체(검색→컨텍스트 조립→답변 생성→웹 화면)를 대상으로,
T5(검색 품질 검증)와 같은 원리를 답변 생성에도 적용해 자동 평가 스크립트
(`scripts/evaluate_rag.py`)를 만들고, 발견된 문제를 튜닝했습니다.

### 평가 방식

1. **근거 인용 확인(cite)**: "연구비 감사 관련 행정사무는 어느 부서가 지원해?" 등 정답이
   있는 질문에서, 검색이 실제로 정답 후보 조항을 가져왔는지 + LLM이 그것을 근거로 실제
   답변했는지(잘못 거절하지 않는지) 확인
2. **숫자 환각 확인**: 답변 문장에 등장하는 숫자가 근거 컨텍스트(참고자료)에도 실제로
   등장하는지 대조 — 컨텍스트 밖의 숫자가 나오면 지어낸 것으로 간주
3. **정확한 거절 확인(refuse)**: 구체적인 답이 없는 질문("연구비 지원 한도가 얼마야?")과
   규정과 완전히 무관한 질문("오늘 서울 날씨가 어때?", "다음주 로또 번호 알려줘")에
   올바르게 거절하는지 확인
4. **응답 시간 측정**

### 발견한 문제와 튜닝

**문제**: 초기 평가에서 규정과 무관한 질문 2건이 모두 실패했습니다. 원인을 추적한 결과,
`search_engine.py`의 관련성 최소 기준(BM25 점수가 0보다 크면 통과)이 검색 결과 "목록
표시"용으로는 적절하지만, "오늘 **서울** 날씨가 어때?"의 '서울'이나 "다음주 로또 **번호**
알려줘"의 '번호' 같은 흔한 단어 하나만 우연히 일치해도 관련 조항인 것처럼 통과시켜, RAG가
불필요하게 LLM을 호출하고("답을 지어낼 위험") 애매한 문서를 근거로 답을 생성하는 문제가
있었습니다.

- 실측 결과: 실제로 관련 있는 질문의 최상위 결과 점수는 **0.74~0.99**, 완전히 무관한
  질문의 최상위 점수는 **0.4**로 뚜렷한 격차가 있었습니다.
- **개선**: `rag_engine.py`에 `MIN_TOP_SCORE_FOR_ANSWER = 0.5` 기준을 추가해, 검색
  최상위 결과의 점수가 이 기준에 못 미치면 LLM을 호출하지 않고 즉시 "찾을 수 없습니다"로
  응답하도록 했습니다. (기존 `search_engine.py`의 검색 결과 "목록 표시" 자체는 변경하지
  않아, T4/T5 검색 화면과 T5 품질 지표에는 영향이 없습니다 — RAG 답변 생성에만 더 엄격한
  기준을 추가로 적용)

| 튜닝 전/후 | "오늘 서울 날씨가 어때?" | "다음주 로또 번호 알려줘" |
|---|---|---|
| 튜닝 전 | ❌ 검색 결과(서울 언급 문서)를 근거로 LLM 호출 (18.5초 소요) | ❌ 검색 결과(번호 언급 문서 5건)를 근거로 LLM 호출 (23.6초 소요) |
| 튜닝 후 | ✅ 즉시 "찾을 수 없습니다" (0.05초, LLM 미호출) | ✅ 즉시 "찾을 수 없습니다" (0.05초, LLM 미호출) |

### 환각 방지 가드레일 추가 (`rag_engine.py`)

LLM이 근거 조항 목록(`related_regulations`)에 없는 규정명을 답변에 인용하면, 답변 내용을
함부로 삭제·수정하지 않고 경고 문구를 덧붙이는 `apply_citation_guardrail()`을 추가했습니다.
(전체 규정명 목록을 길이 내림차순으로 매칭해, 짧은 규정명이 긴 규정명의 부분 문자열이라서
오탐되는 것을 방지)

```

          경상국립대학교 장학금 규정 제5조에 따라 지원됩니다.
[적용 후] (위 문장) + "⚠️ [자동 검증 경고] 이 답변에는 근거 조항 목록에 없는 규정명
          (경상국립대학교 장학금 규정)이 포함되어 있습니다. 실제 근거 조항을 기준으로
          다시 확인해주세요."
```

## T10 — RAG 운영 체계 마련 (로그·비용·장애대응·매뉴얼)

T6~T9에서 만든 RAG 기능을 실제로 운영에 올려도 안심할 수 있도록, 질문·답변 기록과
장애 대응, 운영 매뉴얼을 정리했습니다.

### 주요 구현 내용

1. **질문·답변 로그 (`data/rag_logs/YYYY-MM-DD.jsonl`)**: `scripts/api_server.py`의
   `/api/ask`가 호출될 때마다 [질문, 근거로 쓴 조항 id 목록, 답변, 응답 시간, 관련 근거
   발견 여부, LLM 실제 사용 여부, 처리 결과(`answered`/`refused`/`fallback_no_llm`/
   `timeout`/`error`), 백엔드(local/external_api)]를 하루 1개 파일에 기록합니다.
   **질문자를 식별할 수 있는 정보(IP·계정·세션 등)는 이 API 자체가 받지 않으므로 저장하지
   않습니다.** 로그 기록이 실패해도 API 응답에는 영향을 주지 않도록 예외 처리했습니다.
2. **호출 횟수·비용 요약 (`scripts/rag_cost_report.py`)**: 위 로그를 읽어 백엔드별
   호출 수, 처리 결과별 분포, 평균 응답 시간을 집계합니다. 외부 유료 API 호출이 있을
   때만 대략적인 예상 비용을 함께 보여주고, **로컬 모델만 쓰는 경우엔 비용 집계가
   불필요함을 화면에 안내**합니다.
3. **장애 대응 강화**: T7에서 이미 있던 "LLM 응답 시간초과 시 검색 결과만 반환" 안전장치
   외에, `/api/ask` 파이프라인에서 **예상치 못한 오류가 발생해도 500 에러로 화면을 막지
   않고 검색 결과만이라도 반환**하도록 `_search_only_fallback()`을 추가해 오류 상황까지
   포함해 검색 전용 모드로 전환되게 했습니다. (검색 엔진 자체마저 응답 불가한 극단적인
   경우에만 최종적으로 500 오류를 반환)
4. **운영 매뉴얼(`MANUAL.md`) RAG 섹션 추가**: 실행 방법(로컬 AI는 별도 설정 없이 자동
   동작, 외부 API로 바꾸려면 환경변수 설정법), 답변이 이상할 때 확인·보고하는 방법,
   로그·비용 확인 방법, LLM 장애 시 자동 대응 안내를 비전공자 기준으로 정리했습니다.

## T11 — 임베딩 모델 교체 시도 (BGE-M3) → 롤백

실제 시연 중 "키워드 검색은 정확한데, 자연어 질문형 질의의 정확도는 아쉽다"는 피드백을
받아, 원인을 분석했습니다.

### 원인 분석

지금까지 써온 **KR-SBERT**는 "두 문장이 서로 비슷한 뜻인가"를 비교하도록 학습된
**대칭적(symmetric) 문장유사도** 모델입니다. 그런데 실제로 하는 일은 **질문**(구어체,
물음표로 끝남)과 **규정 조문**(딱딱한 법조문체)처럼 문장 형태가 크게 다른 것을
비교하는 **비대칭 검색(asymmetric retrieval)** 이라, 키워드가 겹치는 검색은 잘
맞지만 질문형 질의는 상대적으로 정확도가 떨어지는 구조적 한계가 있었습니다.

### 시도: BGE-M3로 교체

"짧은 질의 ↔ 긴 문서"를 검색하는 용도로 학습된 다국어 검색 전용 모델(한국어 포함)인
**BAAI/bge-m3**로 임베딩 모델을 교체하고 벡터DB(9,258개 청크)를 재구축했습니다.

### 실측 결과: 부작용 발견 → 롤백 결정

| 질문 | KR-SBERT 점수 | BGE-M3 점수 |
|---|---|---|
| "주식 시세 알려줘" (완전 무관) | ~0.3~0.4 | **0.93** |
| "다음주 로또 번호 알려줘" (완전 무관) | 0.4 | **0.70** |
| "점심 뭐 먹지" (완전 무관) | (미측정) | **0.60** |
| 실제 관련 있는 질문들 | 0.74~0.99 | 0.88~0.99 |

BGE-M3로 교체하니 **완전히 무관한 질문의 점수와 실제 관련 있는 질문의 점수 구간이
겹쳐버렸습니다.** 이 모델을 별도 설정(질의문 전용 프롬프트 등) 없이 단순하게 쓰면,
문장 간 코사인 유사도가 전반적으로 높게 압축되어 나오는 경향이 있어, T9에서 어렵게
만든 "무관한 질문은 답을 지어내지 않고 거절한다"는 안전장치(`MIN_VEC_SIM`,
`MIN_TOP_SCORE_FOR_ANSWER`)가 사실상 무력화되는 것을 확인했습니다. 게다가 애초
목표였던 질문형 정확도 자체도 뚜렷하게 개선되지 않았습니다(일부 사례는 오히려 오답에
대한 확신도만 더 높아짐). **정확도 개선 효과보다 환각 방지 안전장치가 깨지는
리스크가 더 크다고 판단해, 임베딩 모델은 KR-SBERT로 즉시 원복했습니다.**

## T12 — 검색 정확도 개선 (재순위화 + 청킹 문맥 강화)

T11의 교훈(모델 통째 교체는 검증된 안전장치를 깨뜨릴 위험이 큼)을 반영해, **기존
KR-SBERT·관련성 기준은 그대로 유지**하면서 정확도만 안전하게 높이는 두 가지를
추가했습니다.

### ① 재순위화 (Re-ranking)

- **원리**: 1차로 하이브리드 검색(의미+키워드)이 후보를 넉넉히 추린 뒤, 상위
  20개만 **cross-encoder**(`BAAI/bge-reranker-v2-m3`)로 "질문"과 "조문 원문"을
  한 쌍으로 직접 비교해 다시 정밀하게 순위를 매깁니다. 임베딩을 각각 벡터로 만들어
  비교하는 기존 방식보다 훨씬 정확하지만, 그만큼 느립니다(후보 20개 기준 수 초~10여 초).
- **속도 문제 해결**: 재순위화를 검색 전체에 적용하면 즉시 응답이 생명인 일반
  검색(`/api/search`)까지 10초 넘게 느려지는 부작용이 있어, **`rerank` 옵션으로
  분리**했습니다.
  - 🔍 **일반 검색**: `rerank=False` (기본값) — 기존과 동일하게 즉시 응답 (T5 기준
    평균 0.04초 유지)
  - 💬 **AI에게 질문하기**: `rerank=True` — 어차피 LLM 답변 생성에 수십 초가
    걸리므로, 재순위화가 추가하는 시간은 상대적으로 부담이 적고 정확도 향상 효과가 더 큽니다
  (`scripts/search_engine.py`의 `search(..., rerank=False)`, `scripts/rag_engine.py`의
  `retrieve()`가 `rerank=True`로 호출)

### ② 청킹 문맥 강화 (장(章) 제목 부여)

- 조문 하나만 봐서는 주제를 알기 어려운 짧은 위임·절차 조항도, **소속된 장(章)
  제목**("제7장 휴학, 복학, 재입학, 편입학, 유급, 퇴학 및 제적" 등)을 함께 임베딩에
  포함시키면 문맥이 보강되어 검색 정확도가 올라갑니다.
- `scripts/chunk_rules.py`가 청킹 시 각 조문 위치를 기준으로 가장 가까운 앞쪽의
  "제0장 ..." 제목을 찾아 `chapter` 메타데이터로 저장하고, `scripts/build_vectordb.py`가
  임베딩 텍스트에 `"{규정명} {장 제목} {조항}({조항 제목})\n{본문}"` 형식으로 포함합니다.

## 🔍 "검색" vs 💬 "AI에게 질문하기" — 뭐가 다른가요? (비전공자용 설명)

화면 위쪽에 있는 두 탭, **"🔍 검색"**과 **"💬 AI에게 질문하기"**는 겉보기엔 비슷해 보여도
내부적으로 완전히 다른 방식으로 동작합니다. 비유로 설명하면 이렇습니다.

> **🔍 검색** = 도서관 사서에게 "이 단어 들어간 페이지 다 찾아주세요"라고 하는 것
> **💬 AI에게 질문하기** = 그 페이지들을 다 읽어본 상담원이 "그거 이런 뜻이에요"라고
> **직접 요약해서 말로 설명**해주는 것

### 한눈에 보는 차이

| 구분 | 🔍 검색 (T1~T5) | 💬 AI에게 질문하기 (T6~T10, RAG) |
|---|---|---|
| **하는 일** | 입력한 단어·문장과 관련된 조항을 **찾아서 목록으로 나열** | 관련 조항을 찾은 뒤, 그 내용을 **AI가 읽고 문장으로 정리해서 답변** |
| **결과 형태** | 조항 카드 여러 개 (규정명·조항 번호·본문 발췌 등) | "~~하려면 ~~해야 합니다" 같은 **완성된 문장** + 근거 조항 카드 |
| **누가 "이해"하는가** | 사람이 카드를 직접 읽고 이해해야 함 | AI가 먼저 읽고 이해한 결과를 사람에게 전달 |
| **걸리는 시간** | 0.1초 내외 (매우 빠름) | 보통 20~80초 (AI가 문장을 만드는 시간 소요) |
| **사용한 기술** | 키워드 검색(BM25) + 의미 검색(임베딩·벡터DB)을 결합한 **하이브리드 검색** | 위 검색 기술 그대로 사용 + **LLM(거대언어모델)** 이 검색 결과를 근거로 답변 문장을 생성 (RAG 방식) |
| **정확성 보장 방법** | 원문 그대로 보여주므로 왜곡 위험 없음 | ① 검색으로 찾은 조항 **안의 내용만** 근거로 쓰도록 제한 ② 그래도 없는 내용을 지어내면(환각) 자동으로 경고 문구 추가 ③ 답변 밑에 **원문 근거 조항을 항상 함께 표시** |
| **이럴 때 사용하세요** | "연구비"처럼 **정확한 단어**로 관련 규정을 빠르게 훑어보고 싶을 때 | "휴학하려면 언제까지 신청해야 해?"처럼 **문장으로 물어보고, 결론만 바로 알고 싶을 때** |

### 그림으로 보면

```
🔍 검색 모드
  사용자 입력 ──▶ [하이브리드 검색] ──▶ 관련 조항 카드 목록 (그대로 표시)

💬 AI에게 질문하기 모드 (RAG = Retrieval 검색 + Augmented Generation 생성)
  사용자 입력 ──▶ [하이브리드 검색] ──▶ 관련 조항 찾기
                                        │
                                        ▼
                              [AI(LLM)에게 "이 내용 안에서만 답해줘"라고 전달]
                                        │
                                        ▼
                         사람이 읽기 편한 답변 문장 + (검증용) 원문 근거 조항 카드
```

즉, **"AI에게 질문하기"도 결국 내부적으로는 "검색"을 먼저 그대로 수행**합니다. 그 검색
결과에 AI가 "요약 한 단계"를 더 얹은 것일 뿐이라, 검색이 못 찾은 내용을 AI가 갑자기
찾아내는 것은 아닙니다 (그래서 검색에서 결과가 없으면 AI도 "찾을 수 없습니다"라고
정직하게 답합니다 — T9에서 이 부분을 집중적으로 검증했습니다).

### 왜 검색 결과를 답변과 항상 같이 보여주나요?

AI가 만든 문장은 참고용이며, 가끔 표현이 어색하거나(드물게) 실수가 있을 수 있습니다.
그래서 **AI의 말만 믿지 말고, 항상 그 아래 근거 조항 원문을 직접 확인**할 수 있도록
설계했습니다. 법적 효력은 언제나 원본 규정 조항에 있습니다.
